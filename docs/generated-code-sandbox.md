# Generated-code sandbox

## Security boundary

iCheck never imports AI- or user-generated Python into the API or Collector
Worker process. The first generated runtime, `python_sandbox_v1`, is deliberately
narrow: a trusted `http_json_sandbox` adapter performs the allowlisted HTTP
request, applies response-size and record limits, and injects credentials only
into that trusted request. The generated function receives normalized JSON
envelopes and non-secret configuration, then returns normalized envelopes.

The default `process` backend launches a fresh isolated Python process for every
validation or collection. Before generated bytecode is evaluated, the stdlib-
only harness applies:

- a strict AST policy: no imports, classes, lambdas, exception machinery,
  indirect calls, dunder access, unbounded `while`, or non-approved methods;
- Landlock with no filesystem allow-rules, denying new reads, writes, directory
  traversal, execution, creation, removal, rename, and truncation;
- seccomp-BPF denial of networking, process creation/exec, ptrace/process-memory
  access, mount/namespace operations, BPF, perf, and other privileged syscalls;
- `no_new_privs`, a 128 MiB address-space cap, two CPU seconds, one process,
  32 file descriptors, bounded input/output, and a parent wall-clock timeout;
- an empty environment, isolated working directory, and a new process session.

The runtime currently targets Linux x86-64 and fails closed when Landlock or
seccomp is unavailable. An optional `bubblewrap` backend adds user/PID/network/
mount namespaces on hosts whose kernel and AppArmor policy permit unprivileged
user namespaces. It is not required by the default backend and iCheck does not
change host AppArmor policy automatically.

## Artifact contract

```json
{
  "implementation": {
    "runtime": "python_sandbox_v1",
    "adapter": "http_json_sandbox",
    "entrypoint": "transform",
    "source": "def transform(records, configuration):\n    return records\n"
  },
  "tests": [
    {
      "name": "normalizes one device",
      "fixture": [
        {
          "kind": "observation",
          "type": "inventory.asset",
          "source": "fixture",
          "payload": {"name": "edge-01"}
        }
      ],
      "configuration": {},
      "expected": [
        {
          "kind": "observation",
          "type": "inventory.asset",
          "source": "fixture",
          "payload": {"name": "edge-01"}
        }
      ]
    }
  ]
}
```

Only `transform(records, configuration)` is accepted. A sandboxed collector
must declare one to 100 exact-output fixtures. Validation runs every fixture in
isolation and persists the runtime, isolation backend, test names, output
counts, output hashes, and durations in `ArtifactVersion.validation_report`.
The generated source, fixtures, and report are covered by the immutable version
workflow; a failed or unavailable sandbox leaves the version in `draft`.

At runtime, Worker capability `http_json_sandbox` is required. The trusted HTTP
adapter runs first, the generated transform runs in a new sandbox process, and
the normal Worker secret-redaction boundary runs before envelopes or errors are
sent to the control plane.

## Configuration

```text
ICHECK_SANDBOX_ENABLED=true
ICHECK_SANDBOX_BACKEND=process
ICHECK_SANDBOX_PYTHON_PATH=/usr/bin/python3
ICHECK_SANDBOX_TIMEOUT_SECONDS=5
```

For an explicitly configured Bubblewrap host:

```text
ICHECK_SANDBOX_BACKEND=bubblewrap
ICHECK_SANDBOX_BWRAP_PATH=/usr/bin/bwrap
```

Both the control plane (fixture validation) and Workers that advertise
`http_json_sandbox` (runtime transformation) must enable a compatible backend.

## Verified acceptance

Automated tests execute the real process backend and prove that:

- safe deterministic fixtures pass and are persisted before publication;
- imports, dunder access, and unbounded loops are rejected;
- filesystem reads, IPv4 socket creation, and `fork()` fail after kernel policy
  activation;
- trusted HTTP collection completes before transformation;
- deployment/runtime adapter identity cannot differ from the immutable
  implementation declaration.

The Capability Studio REST Collector Designer uses this boundary from
`/studio`; see `docs/capability-studio.md`. Semantic diff, immutable historical
replay, bounded canary rollout, governed fleet replacement/rollback, and
health-gated rollout rings are implemented. Generated Tool Artifacts use the
separate declarative MCP contract/attestation/activation boundary; arbitrary
generated executable Tool code is deliberately not a supported runtime.
