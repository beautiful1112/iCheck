# Prometheus metric alerts

iCheck prepares and retains threshold rules; Prometheus evaluates them and
Alertmanager delivers notifications to the iCheck alert inbox. Inventory-event
rules retain their existing evaluator. Metric rules never enter that evaluator,
and routine samples remain in Prometheus rather than PostgreSQL.

The current paired preview and native Alertmanager are deployed on this server.
The managed catalog, private lifecycle API, receiver service identity and
supporting GUI passed live setup checks. No rule, target or fault was created by
deployment, so actual notification delivery remains unverified. See the
deployment receipt (private development evidence; not distributed).
A private native Prometheus and Alertmanager
pipeline delivered firing and cleared notifications, and private PostgreSQL
migration and history checks passed. These results do not qualify a lab device
or substitute for a live controlled-fault journey.

## Alertmanager management

The management page at `/alerts/alertmanager`, linked from Monitoring, Alert
evidence and Prometheus metric rules, shows native readiness, active rule-bound
notifications, sanitized receiver types and routes, maintenance silences, and the
latest 100 accepted iCheck inbox receipts. Deployed r19.9 passed authenticated live
readiness/configuration checks. Reviewed silence creation/ending passed a rendered
fixture and an isolated native Alertmanager, not the running monitoring service.

Administrators can review and confirm a silence for one enabled rule revision,
for 1–1,440 minutes. Exact workspace and revision matchers are generated by iCheck;
the browser cannot submit wildcard matchers. Ending a silence also requires review.
Silencing affects notifications, not collection, rule evaluation, acknowledgement
or fault recovery. Broader externally managed silences can suppress notifications
but are not editable on this scoped page.

The existing PostgreSQL audit log retains each request before native I/O. A lost
response remains unconfirmed; **Inspect outcome without resending** reads native
state without repeating a write. Reusing the same request key cannot issue a
second native mutation. The native API remains loopback-only and is never proxied
directly to the browser. No SQL migration or second evaluator is added.

Receiver destinations and credentials are hidden; receiver/route editing remains
protected native configuration in this preview. Delivery history means accepted
webhook receipts in iCheck, not email/SMS delivery. Separate native counters show
cumulative attempts and failures, including retries. Readiness alone does not
prove delivery, and unavailable sections display a diagnostic instead of claiming
a healthy or quiet system.

## Engineer workflow

1. Enable an approved monitoring template and verify its actual fresh measurements
   in Capability Studio. Save its target-specific Grafana dashboard.
2. Open **Alert evidence → Prometheus metric rules**, or ask AI to prepare a
   threshold. Select the exact enrollment and a declared measurement. Thresholds
   use reported units; counters use a rate window, gauges use their current value.
   A raw counter is not a rate, and an arbitrary gauge is not a percentage.
3. Test samples and inspect the proposed target, comparison, hold time, severity
   and saved Grafana link. This test does not prove notification delivery.
4. Confirm the exact preview as a signed-in human with global `alerts.admin` and
   `metrics.manage`. iCheck validates the native rule, replaces only its managed
   rule catalog, reloads Prometheus and verifies the loaded definitions.
5. Induce a controlled threshold breach. Inspect the actual Alertmanager receipt
   in Alert evidence, open its saved Grafana dashboard, or prepare an investigation.
   Investigation links populate a draft; they do not automatically run the AI.

AI uses three native tools in the existing registry: approved target discovery,
sample-tested rule preview and retained-change inspection. There is no AI rule
confirmation tool. A separate MCP server or second agent loop is unnecessary.
The tools return the current configured backend and human review URL without
notification credentials. Scoped investigations cannot use namespace-wide rule
management.

## Revision and withdrawal

Edit a retained rule to prepare a new revision. Its name remains a stable identity.
Uncheck **Enable after confirmation** to withdraw an existing rule; withdrawal
retains its definition and works when the monitored source is unavailable.
Version history can preview an earlier definition as a new revision, with fresh
source validation and a new human confirmation.

An uncertain write retains an `unknown` or `applying` receipt. **Inspect previous
write** compares the existing managed file and loaded Prometheus rules; it does
not repeat the file replacement or reload. A conflicting catalog requires a fresh
preview. Do not manually overwrite the managed file to hide an uncertain result.

## Notification semantics

Acknowledging an episode records human receipt; it does not clear the Prometheus
condition. Alertmanager `resolved` means that Prometheus stopped reporting that
condition. Missing data, source withdrawal or an evaluation change can also cause
clearance, so iCheck records infrastructure recovery as **unverified** and does
not manufacture recovery evidence. The Grafana link is the retained saved dashboard
for the selected source and measurement, not a guessed overview URL.

The receiver accepts only its configured service bearer identity and complete,
bounded notifications matching a retained applied rule revision and namespace.
Firing additionally requires current monitoring authority. Rule identity, links
and descriptions come from iCheck's reviewed definition, not untrusted webhook
annotations. Repeated and late notifications preserve episode ordering. Human
tokens, generic alert emission and manual resolution cannot bypass this boundary.

The first destination is the iCheck inbox, not email, SMS or Slack. An additional
Alertmanager receiver requires its own protected configuration and observed
delivery. Receiver configuration alone is never delivery evidence.

## Native deployment preparation

The source examples under `deploy/alertmanager/` are packaged under
`config/alertmanager/`; optional systemd drop-ins are under
`operator/deploy/systemd/` in the native bundle. These files are
deployment inputs, not installed runtime state. Review them against the actual
server configuration before a backed-up, coordinated application migration.
The current source and running schema head are `w0c2e4g6i8k1`. On another server,
deploy the paired backend and GUI before exposing this page.
Never upgrade the live database to an unrelated source head independently of its
application release.

Use the existing Prometheus instance and preserve all scrape jobs and retention.
Merge one `rule_files` entry and the Alertmanager destination from
`prometheus-alerting.yml.example`. The optional Prometheus drop-in enables the
fixed loopback lifecycle endpoint; it must not be exposed through the public proxy.
That endpoint is not independently authenticated and assumes a trusted lab host.
For the management page, provision `ICHECK_METRIC_ALERTMANAGER_URL=http://127.0.0.1:9093`
for the control plane alongside its existing exact backend/workspace binding.
The reviewed upgrade helper's `--enable-alertmanager-management` option adds a
fixed service override for this existing native service; it does not replace
receiver configuration, create silences or enable targets.

Provision `/var/lib/icheck-metric-rules` owned by the control-plane account `icheck`,
group `icheck-prometheus`, mode `2750`. The fixed `rules.yml` is API-owned, group
Prometheus-readable, mode `0640`; initialize it from the empty catalog example.
The directory's set-group-ID bit ensures atomic replacement preserves the reader
group even with the API's restrictive umask. The private lock stays mode `0600`.
Add the control-plane writable-path drop-in and reviewed environment values for
the exact backend, tenant and region. No browser field accepts a filesystem path.

Install the verified native Alertmanager binary as a separate unprivileged
`icheck-alertmanager` service. Keep listener `127.0.0.1:9093`, clustering disabled
and state in `/var/lib/icheck-alertmanager`, mode `0700`. Do not expose its API
or add another metrics store. The example service does not require Docker.

Create a dedicated service principal with global `alerts.emit` and `assets.read`
in the selected trusted workspace. Issue an expiring service token directly into
the protected receiver file using an authenticated deployment session; never use
the administrator token. Store that file for the Alertmanager account only,
mode `0600`, and keep its parent inaccessible to other users. Match the principal's
subject to `ICHECK_METRIC_ALERT_WEBHOOK_SUBJECT`. The token is read server-side
through `credentials_file`, never pasted into YAML, chat, URLs or browser storage.
Plan token rotation before expiry.

Validate the merged configuration with native `promtool check config` and
`amtool check-config`, start the reviewed services, and then verify one controlled
firing/cleared receipt through the GUI. `/metric-alerts/setup` reports provisioning
only; it deliberately does not claim delivery.

## Backup and removal

Back up the PostgreSQL definitions/receipts, managed rule catalog, Alertmanager
state and protected configuration together. Preserve active application rollback
releases and service credentials separately under their existing custody rules.
Migration downgrade refuses populated metric-rule history rather than discarding it.

Before removal, withdraw each managed metric rule and verify that Prometheus no
longer loads it. Remove only the managed rule-file and alerting integration, stop
the dedicated Alertmanager service, and revoke its service token. Preserve native
state and SQL history until an operator explicitly authorizes deletion. Do not
remove Prometheus, exporters, their jobs, existing inventory rules or Grafana.

## Focused verification

The reusable checks include `tests/test_alertmanager_management.py`, `tests/test_metric_alerts.py` and
`tests/test_metric_alert_migration.py`. Native engine tests are opt-in through
`ICHECK_METRIC_ALERT_TEST_PROMETHEUS_BINARY`,
`ICHECK_METRIC_ALERT_TEST_ALERTMANAGER_BINARY` and
`ICHECK_METRIC_ALERT_TEST_POSTGRES_BIN`; they use temporary loopback services or
a socket-only database, not the live TSDB/database. GUI checks use explicitly
mocked source APIs. Keep source, deployed and real-device qualification separate.

Native configuration follows the official
[Prometheus alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)
and [Alertmanager webhook configuration](https://prometheus.io/docs/alerting/latest/configuration/#webhook_config).
Management uses the installed version's
[Alertmanager v0.34.1 API](https://github.com/prometheus/alertmanager/blob/v0.34.1/api/v2/openapi.yaml).
